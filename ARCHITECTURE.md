# Архитектура

Сервис превращает шаблон презентации и текстовый контент в готовую колоду —
без ручного редактирования и без знания о шаблоне заранее. Всё, что касается
оформления, извлекается из загруженного файла; всё, что касается смысла,
делает модель под контролем детерминированных проверок.

Правило разделения ответственности одно на весь проект: **модель отвечает за
смысл, код — за пиксели.** Модель планирует историю, сокращает подписи и
отвечает на вопросы аудита о смысле; код считает ёмкость слотов по метрикам
шрифтов, подбирает макеты, укладывает текст, собирает файл и проверяет его.
Если модель недоступна, конвейер проходит целиком на эвристиках: страдает
история, не вёрстка.

## Слои

                     │ + паттерны   │        │ план истории  │

                              ┌────────────────┐
                              │ 3. Вёрстка     │  матчер (венгерский алгоритм) →

### 1. Разбор шаблона — `sd/ooxml`, `sd/template`, `sd/render`, `sd/vision`

Шаблон читается как пакет OOXML: тема, мастера, макеты, слайды-примеры,
встроенные шрифты. Из него собираются два артефакта.

**Дизайн-система** (`DesignSystem`): палитра со слотами темы и провенансом
каждой роли (`accent_primary #0077FF ← theme.accent1`), пары шрифтов и
типографическая шкала, поля, направляющие и безопасная зона, декор. Ёмкость
текста считается по настоящим метрикам шрифта (`cmap`/`hmtx` через fontTools),
поэтому «сколько знаков влезет» зависит от гарнитуры, кегля и языка.

**Библиотека паттернов** (`Pattern`): каждый макет и каждый слайд-пример
превращаются в набор слотов с ролями (`title`, `item`, `metric_value`,
`chart`…), ёмкостью и повторяющимися группами; паттерну присваивается архетип
(`cover`, `bullets`, `metrics`, `two_column`, `table`, `chart`…) с объяснением.
Рендер пустых макетов (PowerPoint COM или LibreOffice) даёт картинку фона, по
которой компьютерное зрение находит препятствия — логотипы, плашки, — которых
нет в XML.

HTML-шаблоны (`.dc.html` из дизайнерского пакета) разбираются той же логикой
в `sd/htmldeck/parse.py`: секции — это паттерны, узлы с текстом — слоты.

### 2. Генерация — `sd/content`, `sd/plan/storyline.py`, `sd/llm`

Контент любого поддерживаемого формата разбирается в **Content IR**: блоки
`heading`, `paragraph`, `list`, `metric`, `table`, `series`, `quote`, `contact`
с идентификаторами. Числа и метрики извлекаются из текста автоматически.

**План истории** (`DeckPlan`) строит модель по промпту `prompts/planner.md`:
состав и порядок слайдов, `intent` каждого, заголовок-вывод, тезисы и ссылки
на блоки. Ответ проверяется по JSON-схеме; план, который не опирается на слова
документа (проверка `grounding`), отбрасывается в пользу эвристики. Модель
спрашивают один раз на колоду; три варианта расходятся уже после неё.

Если на входе не контент-пакет, а краткий бриф (меньше 120 слов и без данных),
работает режим автора (`prompts/writer.md`): модель сама пишет структуру под
назначение — фича, продукт, проект, отчёт — и текст слайдов. Такой план
помечен `authored`, в заметках колоды об этом сказано, а числа, которых нет в
брифе, из тезисов вырезаются.

### 3. Вёрстка — `sd/plan/match.py`, `sd/fit`, `sd/compose`, `sd/plan/variants.py`

**Матчер** назначает паттерн каждому слайду по всей колоде сразу (венгерский
алгоритм), чтобы лучшие макеты не доставались первым слайдам. Оценка
раскладывается на слагаемые — архетип, ёмкость, медиа, повтор, риск
переполнения, плотность — и показывается в интерфейсе.

**Укладка** (`sd/fit/layout.py`) кладёт тезисы и блоки в слоты: считает
строки по метрикам, спускается по типографической шкале шаблона, если текст
не влезает, режет карточки, ставит цифру над подписью, и только в конце
сокращает текст — сначала моделью (`prompts/shortener.md`), потом обрезкой
по словам. Что не поместилось никуда, честно уходит в «не размещено».

**Сборка** (`sd/compose/deck.py`) — копия шаблона без слайдов-примеров, в
которую слайды добавляются двумя способами: `use_layout` (плейсхолдеры макета)
и `clone_slide` (копия слайда-примера с подменой содержимого). Таблицы и
графики — нативные объекты, редактируемые в PowerPoint.

**Схема процесса и пиктограммы** (`sd/template/synthetic.py`,
`sd/compose/diagram.py`, `sd/icons/`). Если под шаги процесса в шаблоне нет
макета, анализатор добавляет синтетический паттерн `process-diagram` на самом
спокойном макете «заголовок + поле»; матчер оценивает его наравне с родными
(с уступкой), укладчик отдаёт ему 3–6 шагов, композитор рисует карточки,
номера, стрелки и пиктограммы нативными фигурами в цветах темы. Библиотека
пиктограмм общая для HTML- и pptx-ветки: контуры SVG переводятся в
`custGeom` (`sd/icons/svgpath.py`, `sd/icons/shape.py`), подбор по смыслу —
`sd/icons/library.py`. Тот же набор закрывает пустые фотослоты макетов.

**Три варианта** одного контента различаются плотностью — сколько мыслей
уносит слайд, нужны ли разделители, какие макеты предпочитать. Это те же
рычаги с тремя настройками, а не три алгоритма; обоснование оси — в
[`docs/07-variants.md`](docs/07-variants.md).

Для HTML-шаблонов слой вёрстки — `sd/htmldeck/build.py`: те же план и слоты,
но результат — разметка, которую браузер потом проверяет на переполнение и
поджимает (`reflow.py`).

### 4. Аудит и ремонт — `sd/qa`

Готовый файл проверяется по чек-листу заказчика (`sd/qa/audit.py`), причём
проверки двух родов явно разделены: **детерминированные** смотрят на файл и
всегда дают один ответ, **контекстуальные** задаются модели
(`prompts/auditor.md`) и на повторе могут ответить иначе. Визуальный
нормоконтроль (`sd/qa/visual.py`) сверяет рендер слайда с рендером его пустого
макета и находит вылезший текст по пикселям. Каждая находка несёт номер
слайда, группу, природу и признак «исправима сборкой». Ремонт — по выбору
пользователя: слайд пересобирается ужатым бюджетом или на макете с большим
числом мест. Подробно — в [`AUDIT.md`](AUDIT.md).

### 5. Экспорт — `sd/render/export.py`, `sd/htmldeck/export.py`

Из pptx-ветки: `.pptx` (рабочий файл), `.pdf` (тем же движком, что рендерит
слайды) и `.html` (самодостаточная страница с кадрами и текстом слайдов). Из
HTML-ветки: `.html` (колода с движком показа), `.pptx` (снимок оформления и
редактируемые надписи поверх, положение которых измерено в браузере) и `.pdf`.

## Точки входа

| Что | Где |
|---|---|
| Один вызов «шаблон + контент → колода» | `sd/pipeline.py`: `build_one`, `build_variants` |
| Пиктограммы и схемы | `sd/icons/` (библиотека, SVG → `custGeom`), `sd/compose/diagram.py` |
| CLI | `python -m sd analyze · preview · plan · build · check · matrix` |
| HTTP API | `sd/api/app.py` — задания на разбор шаблона и сборку, карточки вариантов, аудит, ремонт, файлы |
| Веб-интерфейс | `frontend/` — React + Vite; dev-сервер проксирует `/api` на бэкенд |
| Промпты и конфиги агентов | `backend/prompts/*.md` — версионируются, версии попадают в отчёт |

## Данные между слоями

Все промежуточные структуры — pydantic-модели с JSON-представлением:
`DesignSystem` и `Pattern` (`sd/template/model.py`), `ContentIR`
(`sd/content/model.py`), `DeckPlan` и `DeckSpec` (`sd/plan/model.py`),
`DeckReport` и `Defect` (`sd/qa/model.py`). Их можно выгрузить и посмотреть —
`sd analyze --out-dir`, `sd plan -v`, `sd check`. Форматы описаны в
[`docs/02-architecture.md`](docs/02-architecture.md).
