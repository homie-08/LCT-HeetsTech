# 01. Разбор задачи

## 1. Формулировка кейса (как дано организаторами)

**Название:** Сервис «Цифровой дизайнер презентаций» — создание качественной
презентации в заданном шаблоне на основе текстового описания.

**Актуальность.** Генеративный ИИ хорошо пишет содержание, но плохо
воспроизводит структуру, визуальные паттерны и дизайн. Чтобы сделать
презентацию в фирменном стиле, нужно разобрать шаблон, выделить дизайн-систему,
понять логику типов слайдов, подобрать паттерн под новый контент и сверстать
результат.

**Требуется:** навык, который анализирует шаблон, извлекает структуру,
дизайн-систему и типовые паттерны слайдов, а затем собирает новую презентацию по
предоставленному контенту. Решение должно адаптироваться к разным стилям и
выдавать готовый результат **без ручного редактирования**.

**Ресурсы (по условию):** Inference API к LLM, 3 шаблона разных стилей, 1 набор
контента, CLI.

**Итог:** open-source решение; результат должен подтверждать, что система
адаптируется к стилю шаблона, **а не работает по заранее зашитым сценариям**.

> ⚠️ Фактически ресурсы не выданы. Шаблоны и контент собираем свои (§8), LLM
> подключаем через адаптер с настраиваемым `base_url` — переключение на API
> организаторов должно быть правкой одной строки в `.env`, не кода.

## 2. Что происходит в реальности — и где именно болит

Типовой процесс подготовки презентации в компании:

| Шаг | Кто | Сколько | Где болит |
|---|---|---|---|
| 1. Собрать содержание (тезисы, цифры, таблицы) | Автор | часы | Это как раз то, что ИИ уже умеет |
| 2. Разложить на слайды, придумать историю | Автор | часы | Нет насмотренности: получается «простыня буллетов» |
| 3. Найти актуальную версию шаблона | Автор | 10–40 мин | Шаблонов несколько версий, берут «тот, что был в почте» |
| 4. Подобрать макет под каждый слайд | Автор | часы | Макетов 20+, автор знает 3 и вставляет всё в «Заголовок и объект» |
| 5. Вёрстка: попадание в сетку, кегли, отступы | Дизайнер | часы–дни | Узкое место: один дизайнер на десятки авторов |
| 6. Правки после ревью бренд-менеджера | Оба | дни | Расползание фирстиля, ручные откаты |

**Где именно проваливаются существующие AI-инструменты.** Gamma, Tome,
Beautiful.ai, Copilot в PowerPoint генерируют слайды **в своих собственных
темах**: содержание приличное, но фирменный шаблон компании либо не
поддерживается, либо «натягивается» подменой палитры и шрифта — декор, сетка и
логика макетов теряются. Причина в том, что у них нет шага **обратного
инжиниринга шаблона**: они умеют «нарисовать красиво», но не «нарисовать как
здесь».

**Ключевой вывод для продукта.** Ценность не в генерации текста, а в связке
«разобрать чужой шаблон → уложить произвольный контент в его правила». Поэтому
центр решения — анализатор шаблона и укладчик, а LLM отвечает только за смысл:
структуру истории и формулировки нужной длины.

## 3. Формальная постановка

Дано:

- **Шаблон** `T` — файл `.pptx` / `.potx`: мастера, макеты, темы (палитра, пары
  шрифтов, стили заливок), плюс, как правило, несколько слайдов-примеров.
- **Контент** `C` — текст произвольной структуры (md / docx / txt), плюс данные
  (csv / xlsx), плюс изображения и описание продукта.
- **Бриф** `B` — необязательный: аудитория, длительность, целевое число слайдов,
  тон, язык.

Найти презентацию `D = (s₁ … s_n)`, где каждый слайд `sᵢ` — экземпляр паттерна
`pᵢ ∈ P(T)` (библиотека паттернов, извлечённая **из самого шаблона**), заполненный
фрагментами контента `Cᵢ`, максимизирующую

```
Q(D) = w₁·Fidelity(D, T) + w₂·Coverage(C, D) + w₃·Narrative(D) − w₄·Defects(D)
```

при жёстких ограничениях:

1. **Стиль только из шаблона.** Любой цвет, шрифт, кегль и координата в `D`
   имеют источник в `T`. Нет источника — значение не появляется.
2. **Ноль дефектов вёрстки.** Ни одного переполнения текстового блока,
   наложения шейпов, выхода за поля и нечитаемого контраста.
3. **Покрытие.** Каждый значимый блок контента попал ровно на один слайд, ничего
   не выдумано сверх `C` (кроме связок и заголовков).
4. **Разнообразие.** Подряд идущие слайды не повторяют один паттерн без нужды;
   использованы паттерны разных архетипов, если контент это позволяет.

---

## 4. Что значит «адаптируется, а не зашито» — операционализация

Это главный критерий кейса, поэтому он должен проверяться механически, а не
словами на защите.

| Требование | Как обеспечиваем | Как показываем жюри |
|---|---|---|
| В коде нет констант стиля | Правило: ни одного HEX-цвета, названия шрифта и абсолютной координаты в модулях генерации; линтер-тест обходит AST и падает при находке | Показать тест `test_no_hardcoded_style.py` |
| Каждое решение отслеживается до шаблона | У каждого применённого значения есть `provenance`: `{"value": "#4472C4", "from": "theme.accent1"}`, `{"bbox": [...], "from": "layout:Раздел/placeholder:title"}` | Открыть JSON-трейс слайда рядом со слайдом |
| Работает на невиданном шаблоне | Держим hold-out: шаблон, на котором ни разу не отлаживались | На защите просим жюри выбрать шаблон из папки, генерируем при них |
| Стиль меняется, контент — нет | Один и тот же контент прогоняется через N шаблонов одной командой | Матрица «контент × шаблон» скриншотами |

**Важное разделение.** Словарь **архетипов** (обложка, разделитель, список,
сравнение, метрики, процесс, таблица, график, цитата, контакты) — это семантика
контента, она универсальна и её знать можно. Всё **визуальное** — палитра,
типографика, сетка, декор, правила отступов — приходит только из шаблона.
Архетип отвечает на вопрос «что показываем», шаблон — «как это выглядит здесь».

## 5. Метрики качества (считаются автоматически)

Без них «получилось красиво» — вкусовщина. Все метрики считает `evaluate.py`
по сгенерированному файлу и рендеру его слайдов.

| Метрика | Как считаем | Цель |
|---|---|---|
| **Palette conformance** | Доля пикселей/заливок, чей цвет ∈ палитре шаблона (с допуском ΔE) | ≥ 98 % |
| **Font conformance** | Доля ранов со шрифтом из пары шаблона | 100 % |
| **Grid alignment** | Доля шейпов, чьи границы попадают в сетку шаблона (±0.5 % ширины) | ≥ 95 % |
| **Overflow rate** | Слайды с текстом за границей блока (по рендеру) | 0 |
| **Collision rate** | Пары непрозрачных шейпов с пересечением > 2 % площади | 0 |
| **Contrast pass** | Доля текстовых блоков с контрастом ≥ 4.5:1 к фактическому фону под ними | 100 % |
| **Pattern diversity** | Число разных паттернов / число слайдов | ≥ 0.5 |
| **Coverage** | Доля значимых блоков контента, попавших в презентацию | ≥ 0.9 |
| **Time to deck** | От загрузки до готового файла | < 3 мин на 15 слайдов |

`Fidelity` для формулы §3 — взвешенная сумма первых трёх; `Defects` — следующих
трёх. Все они же работают как **функция ремонта**: пока метрика не в норме,
слайд возвращается в цикл исправления.

## 6. Что увидит жюри (обещания демо)

1. Загружаем незнакомый шаблон → сервис за секунды показывает извлечённую
   дизайн-систему: палитру с ролями, шкалу кеглей, сетку, найденные паттерны с
   миниатюрами. Это уже само по себе демонстрирует «разбор», а не угадывание.
2. Загружаем контент → показываем план истории (слайд ↔ смысл ↔ выбранный
   паттерн ↔ почему выбран).
3. Генерируем → скачиваем `.pptx`, открываем в PowerPoint: правится как обычная
   презентация, текст в плейсхолдерах, графики нативные.
4. Меняем шаблон на другой → тот же контент выглядит принципиально иначе.
5. Показываем отчёт нормоконтроля: ноль переполнений, ноль коллизий, палитра и
   шрифты — 100 %.

## 7. Риски и как снимаем

| Риск | Вероятность | Чем бьём |
|---|---|---|
| Шаблон без нормальных макетов (всё нарисовано руками на слайдах) | Высокая | Паттерны извлекаем не только из макетов, но и из слайдов-примеров; режим `clone_slide` копирует готовый слайд и подменяет содержимое |
| Текст не влезает: у кириллицы другая ширина, чем у примеров | Высокая | Реальные метрики шрифта (fontTools) + автофит + переписывание текста LLM под лимит символов + проверка по рендеру |
| Шрифта шаблона нет в системе на машине жюри | Средняя | Метрики берём из встроенного файла шрифта, если он вшит в pptx; иначе метрически совместимая замена и запись в отчёт |
| LLM выдаёт разметку не по схеме | Средняя | Все ответы — строгий JSON Schema + валидация + повтор; смысловые шаги изолированы, вёрстка от LLM не зависит |
| API организаторов медленное или лимитированное | Средняя | Батчинг, кеш ответов по хешу контента, офлайн-режим на детерминированном планировщике |
| Рендер для проверки недоступен (нет PowerPoint/LibreOffice) | Средняя | Три бэкенда рендера, деградация до встроенного SVG-приближения; метрики геометрии считаются и без растра |
| Демо на чужой машине | Средняя | Никакого Docker и тяжёлых зависимостей, всё стартует двумя командами; заранее сгенерированные артефакты как запасной план |

## 8. Чем заменяем невыданные ресурсы

**Шаблоны.** Локально доступны 6 настоящих `.potx` (Pitchbook, Training,
QuizShow, WidescreenPresentation, два фотоальбома) и 10 тем `.thmx` — принципиально
разные по палитре, шрифтам, декору и сетке. Плюс делаем 2–3 своих шаблона в
«корпоративном» духе (тёмная обложка, акцентная плашка, логотип, плотная сетка),
потому что именно такие обычно дают на защите. Один шаблон держим **hold-out** —
на нём не отлаживаемся до самой защиты.

**Контент.** Готовим 3 набора разной формы, чтобы проверять именно подбор
паттернов: (а) описание продукта с метриками и таблицей, (б) отчёт с
данными для графиков, (в) «рыхлый» текст без структуры — проверка планирования.

**LLM.** Адаптер с OpenAI-совместимым интерфейсом: `base_url` + `model` +
`api_key` из `.env`. Пока endpoint не выдан, работаем на своём ключе; для тестов
и офлайн-демо есть детерминированный провайдер-заглушка.

---

## 9. Границы MVP

**Делаем:** `.pptx`/`.potx` на вход и выход; текст, списки, метрики, таблицы,
нативные графики, изображения; русский и английский контент; веб-интерфейс + CLI.

**Не делаем:** генерацию картинок нейросетью (берём изображения из контента и
шаблона), анимации и переходы, редактирование презентации в браузере, PDF на
вход как шаблон (кандидат в стретч-цель — путь «только CV», он же красиво
доказывает адаптивность).
