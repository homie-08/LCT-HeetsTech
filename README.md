# Цифровой дизайнер презентаций

Кейс ЛЦТ 2026. Сервис принимает **шаблон презентации** (`.pptx` / `.potx`) и
**текстовый контент**, разбирает шаблон на дизайн-систему и библиотеку паттернов
слайдов, планирует историю по контенту, подбирает под каждый слайд подходящий
паттерн и собирает готовый `.pptx` — без ручного редактирования.

Ключевая проверка кейса: система должна **адаптироваться к стилю произвольного
шаблона**, а не работать по зашитым сценариям. Поэтому пайплайн нигде не знает
цветов, шрифтов и раскладок заранее — всё извлекается из загруженного файла.

## Стек

**Backend:** Python 3.11 · FastAPI · python-pptx + lxml · Pillow / OpenCV / scikit-image · fontTools
**Рендер:** PowerPoint COM (эталон, Windows) → LibreOffice headless (переносимо) → встроенный SVG (без зависимостей)
**LLM:** адаптер под OpenAI-совместимый endpoint, ключ и base_url — из `.env`; есть офлайн-режим для тестов
**Frontend:** React 18 · TypeScript · Vite · Tailwind
**Без Docker** — всё поднимается локально.

## Быстрый старт

Одним файлом — окружение, зависимости, сборка интерфейса и сервер на
<http://127.0.0.1:8021/> (настройки — в `.env`, шаблон `.env.example`):

```bash
run.cmd
```

На macOS/Linux — `./run.sh`. Дальше — то же по шагам, если нужен только
бэкенд или CLI.

Окружение (один раз):

```bash
py -3.11 -m venv backend/.venv && backend/.venv/Scripts/python.exe -m pip install -r backend/requirements.txt && backend/.venv/Scripts/python.exe -m pip install -e backend --no-deps
```

Последний шаг ставит пакет в режиме разработки: команды ниже пишутся от корня
репозитория, и без него `python -m sd` оттуда не найдёт модуль.

Собрать локальный набор шаблонов:

```bash
backend/.venv/Scripts/python.exe templates/fetch_local.py
```

Заготовки Office — деловые и довольно старые. Современные шаблоны делаются из
тем оформления: `.thmx` — это дизайн-система без макетов, PowerPoint достраивает
по ней полный набор мастеров. Так из десяти установленных тем получаются десять
непохожих шаблонов, и это же лучшая проверка адаптивности:

```bash
backend/.venv/Scripts/python.exe templates/from_themes.py
```

Разобрать шаблон (или сразу все) и выгрузить дизайн-системы:

```bash
backend/.venv/Scripts/python.exe -m sd analyze templates/deck --out-dir data/design
```

Отрендерить шаблон и собрать контрольный лист — рендер каждого паттерна с
разметкой найденных слотов поверх него (`data/previews/<шаблон>/index.html`):

```bash
backend/.venv/Scripts/python.exe -m sd preview templates/deck
```

Разобрать контент, спланировать историю и подобрать паттерны шаблона:

```bash
backend/.venv/Scripts/python.exe -m sd plan templates/deck/Pitchbook.potx data/content/product -v
```

Собрать презентацию:

```bash
backend/.venv/Scripts/python.exe -m sd build templates/deck/Pitchbook.potx data/content/product --out data/out/deck.pptx
```

Прогнать один контент через все шаблоны сразу — сводка ложится в
`data/out/matrix/index.html`:

```bash
backend/.venv/Scripts/python.exe -m sd matrix data/content/product
```

Проверить уже собранный файл:

```bash
backend/.venv/Scripts/python.exe -m sd check data/out/deck.pptx --template templates/deck/Pitchbook.potx --content data/content/product
```

Тесты:

```bash
backend/.venv/Scripts/python.exe -m pytest backend/tests -c backend/pytest.ini --rootdir=backend
```

## Веб-интерфейс

Собрать фронтенд один раз — и дальше всё поднимается одной командой: FastAPI
раздаёт собранный интерфейс с того же порта, что и API.

```bash
npm install --prefix frontend && npm run build --prefix frontend
```

```bash
backend/.venv/Scripts/python.exe -m uvicorn sd.api:app --port 8021
```

Интерфейс открывается на <http://127.0.0.1:8021/>. Для разработки фронта удобнее
dev-сервер с горячей перезагрузкой — он ходит в тот же бэкенд через прокси:

```bash
npm run dev --prefix frontend -- --port 5175
```

Тесты интерфейса (ветки отказа: не тот файл, недоступный сервис):

```bash
npm test --prefix frontend
```

Интерфейс проводит по трём шагам: загрузить шаблон → загрузить контент →
получить презентацию. На каждом видно то, что обычно спрятано внутри:

- **дизайн-система** — палитра со слотами темы и происхождением каждой роли
  (`accent_primary #D19049 ← theme.accent6`), пары шрифтов, шкала кеглей, сетка;
- **галерея паттернов** — рендер каждого макета с наложенной разметкой слотов
  и признаками, по которым определён архетип;
- **результат** — слайды с разложением оценки («архетип 1.00 · ёмкость 0.93 ·
  повтор −0.00»), метрики нормоконтроля и кнопка скачивания.

Кнопки демо-шаблонов и демо-контента собирают презентацию без загрузки файлов —
для защиты, где важна каждая секунда.

Порт бэкенда 8021 задан в `frontend/vite.config.ts` (8000 и 8010 в этом
репозитории заняты соседними проектами).

## Нормоконтроль

Готовый файл проверяется дважды: по разметке и по рендеру. Метрики из
[`docs/01-task-analysis.md`](docs/01-task-analysis.md) §5 считаются на каждой
сборке, дефекты попадают в отчёт с номером слайда и координатами.

| Шаблон | Шрифты | Палитра | Переполнений | Коллизий | Разнообразие | Покрытие |
|---|---|---|---|---|---|---|
| Pitchbook | 100 % | 100 % | 0 | 0 | 0.92 | 75 % |
| Training | 100 % | 100 % | 0 | 0 | 0.75 | 83 % |
| QuizShow | 100 % | 100 % | 0 | 0 | 0.67 | 75 % |
| WidescreenPresentation | 100 % | 100 % | 0 | 0 | 0.83 | 83 % |
| ClassicPhotoAlbum | 100 % | 100 % | 0 | 0 | 0.83 | 83 % |
| ContemporaryPhotoAlbum | 100 % | 100 % | 0 | 0 | 0.83 | 75 % |

**Как ищутся дефекты.** Слайд сравнивается с рендером его же пустого макета:
всё, что появилось поверх, — наш контент, и если он оказался вне слотов, значит
текст вылез за границы. Дальше работает цикл: слайды с дефектами пересобираются
с ужатым бюджетом ёмкости (82 %, затем 68 %), и так до тех пор, пока рендер не
станет чистым. Если слот физически мал для текста, он остаётся пустым, а
фрагмент уходит в «не размещено» — это честнее, чем текст поверх фотографии.

Контраст считается, но помечается как сведения, а не ошибка: цвет текста и фон
мы не выбираем, оба приходят из шаблона.

## Как собирается файл

Выходной `.pptx` — это **копия шаблона** с удалёнными слайдами-примерами: тема,
мастера, макеты, встроенные шрифты и размер слайда наследуются, воспроизводить
их нечем и незачем. Дальше на каждый слайд работает один из двух режимов:

| Режим | Когда | Что происходит |
|---|---|---|
| `use_layout` | паттерн снят с макета | `add_slide(layout)` и заполнение плейсхолдеров — форматирование приходит из шаблона само |
| `clone_slide` | паттерн снят со слайда-примера | слайд копируется целиком вместе с оформлением, содержимое подменяется, связи переносятся в новый пакет |

Графики и таблицы вставляются нативными объектами: они берут акценты темы и
правятся в PowerPoint. Ряды несопоставимого масштаба на один график не кладутся —
столбик «6 дней» рядом с «24 100 заявок» просто не виден.

**Схема процесса и пиктограммы.** Макета под шаги процесса нет ни в одном из
трёх шаблонов организаторов — а у слайдов «как это работает» он нужен. Поэтому
анализатор добавляет синтетический паттерн: самый спокойный макет «заголовок +
поле» (фон под полем проверяется по картинке макета), а композитор рисует в
поле схему из фигур — карточки со скруглением, номер в кружке, пиктограмма по
смыслу шага, стрелки; от пяти шагов — два ряда змейкой. Всё это нативные
фигуры в цветах темы (`schemeClr` с прозрачностью), редактируемые в
PowerPoint. Пиктограммы — свой набор из 34 контуров в манере Lucide,
переведённых из SVG в `custGeom`; тот же набор ставится в пустые фотослоты
макетов и подбирается по словарю смысла. Матчер даёт схеме небольшую уступку
перед родными макетами шаблона и берёт её не больше двух раз на колоду.

На `Pitchbook` из 12 слайдов 11 собираются макетами и 1 клонированием,
на `WidescreenPresentation` — 8 и 4: соотношение диктует шаблон, а не код.

## HTML-шаблоны и экспорт

Вторая ветка работает с колодами `.dc.html` — теми, что отдаёт дизайнерский
пакет. Оформление там держится на CSS-градиентах, `clip-path`, SVG и веб-шрифтах,
и разобрать его в фигуры OOXML без потерь нельзя. Поэтому колода собирается в
HTML (`sd/htmldeck`), а в PowerPoint уезжает так:

| Что | Как | Почему так |
|---|---|---|
| оформление | снимок слайда во всю площадь | иначе теряются градиенты, обводки и SVG — то, ради чего шаблон и берут |
| текст | настоящие надписи поверх снимка | презентацию правят перед выступлением; текст в картинке не правится |
| заметки | подпись макета | видно, из какого паттерна собран слайд |

Положение, кегль, цвет и выключка надписей снимаются в браузере — он один знает
результат вёрстки. Измерение идёт долями от площади слайда, поэтому размер окна
и масштаб сцены на итог не влияют. Фон снимается отдельным проходом, где у тех же
узлов текст сделан прозрачным: не `visibility`, иначе вместе с подписью пропал бы
фон карточки, заданный на том же элементе. Если браузера нет или разметка чужая,
остаётся прежний путь — цельный снимок и текст в заметках.

Подписи внутри SVG остаются частью картинки: они держатся на своих системах
координат и `text-anchor`, и текстовым полем их не повторить — диаграммы важнее
правок.

### Подгонка по вёрстке

Сколько текста влезет в слот, по длине образца шаблона не узнать: та же подпись
в узкой карточке займёт вчетверо больше строк, чем в широкой. Оценка по знакам
поэтому всегда перестраховывается и обрывает фразу там, где место ещё было.

Поэтому последнее слово о размерах остаётся за вёрсткой. Собранная колода
открывается в браузере, и для каждого слайда проверяется одно: помещается ли
содержимое. Если нет — кегль уменьшается, как поступил бы дизайнер, пока не
поместится или пока не упрётся в предел читаемости; и только то, что не влезло
даже там, укорачивается — по слову с конца самой длинной подписи, ровно до
того места, где вёрстка сойдётся. Правки возвращаются адресами узлов и вносятся
в разметку так же, как их находят слоты.

На школьном докладе про трение это сняло 8 обрывов из 10: текст, который счёт по
знакам считал не влезающим, на слайде помещался целиком. Без браузера остаётся
прежний путь — обрезка по оценке, и о ней сказано в отчёте.

## Три варианта вёрстки

Одно задание собирает три колоды на одном шаблоне и одном плане истории —
сжато, сбалансированно, просторно. Ось различий — плотность: сколько тезисов
уносит слайд, нужны ли разделители, какие макеты предпочитать. Модель
спрашивают один раз; варианты расходятся уже после неё, и просторный не
разрастается дальше полутора длин плана и потолка ТЗ в 15 слайдов (или числа, заданного пользователем). Обоснование оси и таблица различий —
[`docs/07-variants.md`](docs/07-variants.md). В интерфейсе — переключатель в
шапке колоды, в CLI — `--variant compact|balanced|spacious|all`.

## Аудит

После сборки каждый вариант проходит чек-лист из Приложения 1 ТЗ:
детерминированные проверки (границы, наложения, поля, шкала кеглей, палитра,
плотность, заглушки, дубли, цифры не из исходника…) и контекстуальные вопросы
модели (вывод ли в заголовке, о том ли слайд, одна ли мысль, связаны ли
соседи). Находки видны в панели «Аудит» с группой, природой и признаком
«исправима сборкой»; выбранные чинятся пересборкой только их слайдов. Что
проверяется, что нет и почему — [`AUDIT.md`](AUDIT.md).

Модель — только с открытыми весами (Apache 2.0 / MIT, до 35B), подробности и
проверенная конфигурация — в [`MODELS.md`](MODELS.md). Ключ и endpoint
берутся из `.env` (шаблон — [`.env.example`](.env.example)), переключение
провайдера — правка одной строки, а не кода:

| Провайдер | Когда | Structured outputs |
|---|---|---|
| `openai_compatible` | Inference API организаторов и любой совместимый endpoint | `json_schema` → `json_object` → схема в промпте, с проверкой в любом случае |
| `stub` | офлайн-демо и тесты | схема выполняется по построению |

Ответ модели всегда проверяется по JSON Schema; при расхождении повтор идёт
с текстом ошибки, а не вслепую. Всё кешируется по хешу запроса — повторный
прогон того же контента даёт тот же результат и не зависит от сети.

Контент-пакет не обязателен: по краткому брифу («запуск чат-бота поддержки:
зачем, как устроен, план внедрения») модель сама пишет структуру и текст
слайдов под назначение — такая колода помечена в заметках, а числа, которых
нет в брифе, в неё не попадают. Без модели по брифу собрать нечего — сборка
так и говорит.

Промпты и конфиги агентов лежат отдельными файлами в
[`backend/prompts/`](backend/prompts/README.md) с версией в шапке; версии
попадают в отчёт каждой сборки и в `/api/status`.

### Переменные окружения

| Переменная | Что задаёт | По умолчанию |
|---|---|---|
| `SD_LLM_PROVIDER` | `openai_compatible` или `stub` (офлайн) | по доступности endpoint'а |
| `SD_LLM_BASE_URL`, `SD_LLM_API_KEY`, `SD_LLM_MODEL` | OpenAI-совместимый endpoint и модель | — |
| `SD_LLM_TIMEOUT` | таймаут одного запроса, с | 180 |
| `SD_LLM_BUDGET_S` | бюджет времени модели на одну сборку, с; по исчерпании сборка идёт без модели | 150 |
| `SD_DATA_DIR` | где хранить задания, колоды и снимки | `data/api` |

## Ограничения

- Рендер, PDF и визуальный нормоконтроль требуют PowerPoint (Windows) или
  LibreOffice; без них колода собирается, а проверки по рендеру честно
  помечаются пропущенными.
- Картинок в контенте нет — макеты с фотографиями получают текст, а
  фотослоты остаются шаблонными; `fill_ratio` на таких макетах не считается.
- Контекстуальный аудит и качество заголовков ограничены моделью 4B; с
  моделью крупнее (см. [`MODELS.md`](MODELS.md)) они точнее без изменений кода.
- Три варианта с моделью на ноутбуке собираются 2–3 минуты; при исчерпании
  бюджета времени часть контекстуальных проверок пропускается с пометкой.
- После перезапуска сервера в списке «недавние» остаются только колоды —
  разобранные шаблоны разбираются заново при следующей сборке.

## Что уже видно на выходе

Разбор одного и того же кода на разных шаблонах даёт разные дизайн-системы —
это и есть проверка «не зашито»:

| Шаблон | Фон | Основной текст | Шрифт | Поля (л/п) | Колонок |
|---|---|---|---|---|---|
| Pitchbook | `#FFFFFF` ← `theme.lt1` | `#000000` ← `theme.dk1` | Calibri | 0.033 / 0.083 | 10 |
| QuizShow | `#6C6C6C` (тёмная основа) | `#FFFFFF` ← `theme.lt1` | Trebuchet MS | 0.025 / 0.075 | 3 |
| ClassicPhotoAlbum | `#3B3B3B` ← `theme.dk2` | `#FFFFFF` ← `theme.lt1` | Century Schoolbook | 0.050 / 0.050 | 5 |
| WidescreenPresentation | `#FFFFFF` ← `theme.lt1` | `#39639D` ← `theme.accent4` | Tw Cen MT | 0.067 / 0.041 | 5 |

Стрелка `←` — провенанс: откуда в шаблоне взято значение. Он хранится в JSON для
каждой роли, чтобы на защите можно было показать источник любого цвета.

Паттерны снимаются с макетов и со слайдов-примеров, каждый — с объяснением
выбора архетипа (`sd analyze … -v`):

```
cover       1.00  Титульный слайд   title subtitle          заголовок ≤48 зн.
two_column  1.00  Сравнение         title item×2 body×2  ↻2 заголовок ≤32 зн.
gallery     0.60  3 сверху, книжная image×3 body×3       ↻3
chart       0.80  slide10.xml       title body chart image   заголовок ≤20 зн.
```

`↻` — эластичная группа: одинаковые боксы с постоянным шагом, такой паттерн
принимает и 2, и 4 элемента. Ёмкость («≤48 зн.») считается по метрикам
настоящего файла шрифта: у кириллицы знак на 17 % шире латинского, поэтому
лимит для LLM должен зависеть от языка и кегля, а не быть константой.

## Зачем здесь компьютерное зрение

Из шаблона собирается «зонд макетов» — презентация, где на каждый макет
приходится один **пустой** слайд. Её рендер показывает ровно то, что шаблон
рисует сам, и по нему находятся препятствия, которых нет ни в одном XML:

```
Pitchbook.potx: препятствий на макетах: 1
  низ справа  (0.8313, 0.9417, 0.0797, 0.0521)  0.4% площади   ← логотип
```

Тонкие линейки-разделители при этом препятствиями не считаются: контент как раз
лежит между ними. Разделяем заливкой замкнутых контуров и морфологическим
открытием — логотип остаётся, линейка исчезает.

## Один контент, разные шаблоны

`sd matrix` строит план истории **один раз** и прогоняет его через все шаблоны:
значит, различия между презентациями объясняются только шаблоном.

| Слайд плана | Pitchbook | Training | ClassicPhotoAlbum | Widescreen |
|---|---|---|---|---|
| cover | `cover` | `cover` | `cover` | `cover` |
| agenda | `agenda` | `bullets` | `image_text` | `bullets` |
| metrics «Проблема» | `metrics` | `image_text` | `gallery` | `image_text` |
| table | `two_column` | `table` | `image_full` | `section` |
| chart | `chart` | `chart` | `image_text` | `image_text` |
| contacts | `bullets` | `section` | `section` | `section` |

Там, где в шаблоне есть подходящий макет, он и выбирается: у Pitchbook — своя
повестка и раскладка под цифры, у Training — таблица и график со слайдов-примеров.
Где такого макета нет, берётся ближайший по структуре, а не «как обычно».

Назначение делает венгерский алгоритм по всей колоде сразу: жадный выбор отдал
бы лучшие макеты первым слайдам. Каждое решение объясняется разложением оценки
(`sd plan … -v`):

```
metrics → metrics «4 сверху: 1 слева, 3 справа»
  архетип 1.00 · ёмкость 0.93 · медиа 0.50 · повтор −0.00 · риск переполнения −0.00 = 2.39
```
