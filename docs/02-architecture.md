# 02. Архитектура и форматы данных

## 1. Пайплайн

```
 шаблон .pptx/.potx ─► [1] Ingest ─► [2] Design system ─► [3] Pattern library ─┐
                                            ▲                     ▲            │
                                            └──── рендер + CV ────┘            │
                                                                               ▼
 контент (md/docx/xlsx/img) ─► [4] Content IR ─► [5] Storyline ─────► [6] Match ─► [7] Fit
                                                     (LLM)            (скоринг)    (LLM+метрики)
                                                                                       │
                                                          deck.pptx ◄── [10] Repair ◄── [9] Validate ◄── [8] Compose
```

Правило разделения ответственности: **LLM отвечает за смысл, код — за пиксели.**
Шаги 5 и 7 (и опционально разметка паттернов в 3) — модельные; 1–4, 6, 8–10
детерминированные. Если LLM недоступна, пайплайн проходит целиком на
эвристиках — деградирует качество истории, не вёрстка.

## 2. Модули

| Пакет | Ответственность |
|---|---|
| `sd/ooxml/` | Пакет OOXML как есть: части, связи, клонирование слайда с медиа, безопасная правка XML мимо python-pptx |
| `sd/template/` | Анализ шаблона: тема, типографика, сетка, декор, библиотека паттернов |
| `sd/render/` | Рендер слайдов в PNG: PowerPoint COM → LibreOffice → встроенный SVG; кеш по хешу файла |
| `sd/vision/` | CV поверх рендера: безопасная зона, переполнения, коллизии, контраст, цветовой диф |
| `sd/content/` | Парсеры входа в Content IR, извлечение таблиц/чисел/изображений |
| `sd/plan/` | Планирование истории (LLM) и подбор паттернов (детерминированный скоринг) |
| `sd/fit/` | Укладка блоков в слоты: метрики текста, автофит, сокращение через LLM |
| `sd/compose/` | Сборка pptx: два режима (`use_layout`, `clone_slide`), графики, таблицы, картинки |
| `sd/qa/` | Метрики из `01-task-analysis.md` §5, отчёт нормоконтроля, цикл ремонта |
| `sd/llm/` | Провайдер (OpenAI-совместимый / заглушка), JSON-схемы, повторы, кеш |
| `sd/api/`, `sd/cli.py` | FastAPI и CLI поверх одного и того же ядра |

Верхнеуровневый сценарий целиком лежит в `sd/pipeline.py` — один вызов
`build_deck(template, content, brief) -> DeckResult`, чтобы CLI, API и тесты шли
одной дорогой.

## 3. Дизайн-система (выход шага 2)

Файл `design_system.json`. Всё, кроме `source`, имеет `provenance` —
откуда в шаблоне взято значение.

```jsonc
{
  "source": {"file": "Pitchbook.potx", "sha256": "…",
             "slide_size": {"w_emu": 12192000, "h_emu": 6858000, "ratio": "16:9"}},

  "palette": {
    "theme": {"dk1": "#000000", "lt1": "#FFFFFF", "dk2": "#1B2A41", "lt2": "#EEF2F7",
              "accent1": "#2F6FED", "accent2": "#F2994A", "accent3": "…",
              "accent4": "…", "accent5": "…", "accent6": "…",
              "hlink": "…", "folHlink": "…"},
    "roles": {                                   // выведены из фактического употребления
      "page_bg": "#FFFFFF", "surface": "#EEF2F7",
      "text_primary": "#1B2A41", "text_muted": "#6B7A8F",
      "accent_primary": "#2F6FED", "accent_on_dark": "#FFFFFF",

    "columns": {"count": 12, "gutter": 0.014},
    "rhythm_y": [0.083, 0.230, 0.310, 0.860],   // кластеры границ шейпов по вертикали
    "safe_area": {"x": 0.062, "y": 0.230, "w": 0.876, "h": 0.630},
    "gaps": {"title_to_body": 0.043, "between_items": 0.021}

    "logos":  [{"image": "media/image2.png", "bbox": [0.86, 0.86, 0.09, 0.06],

```

Как получаем:

- **Палитра, шрифты, фоновые стили** — `ppt/theme/theme1.xml` (`clrScheme`,
  `fontScheme`, `fmtScheme`), плюс переопределения `clrMapOvr` на мастере.
- **Роли цветов** — по фактическому употреблению: цвет фона мастера → `page_bg`,
  цвет самого крупного текстового плейсхолдера → `text_primary`, самый частый
  акцент в декоре → `accent_primary`. Здесь же считается `usage`.
- **Стили текста** — `txStyles` мастера (`titleStyle`/`bodyStyle`/`otherStyle`) как
  база, поверх — фактические `rPr` в плейсхолдерах макетов и слайдов-примеров;
  побеждает мода (самое частое значение), а не первое встреченное.
- **Сетка** — одномерная кластеризация левых/правых/верхних/нижних границ всех
  шейпов по всем макетам и слайдам с допуском 0.5 % стороны; кластеры с
  поддержкой ≥ 3 становятся направляющими, шаг между ними даёт колонки и гаттер.
- **Декор и безопасная зона** — шейпы макета, не являющиеся плейсхолдерами
  контента (плашки, линии, логотипы), плюс проверка по рендеру: рендерим **пустой
  макет**, находим непустые области → это декор, наибольший свободный
  прямоугольник → `safe_area`. CV-проверка ловит то, чего нет в XML (например,
  картинку фона с рамкой).

## 4. Библиотека паттернов (выход шага 3)

Паттерн — это раскладка одного слайда, снятая с шаблона: где что лежит, каким
стилем и сколько туда влезает.

```jsonc
{
  "id": "metrics-3",
  "archetype": "metrics",             // cover | section | agenda | bullets | two_column |
                                      // comparison | metrics | process | table | chart |
                                      // quote | image_full | image_text | gallery |
                                      // team | contacts | blank
  "source": {"kind": "layout", "name": "Три объекта", "idx": 7},
  "render_mode": "use_layout",        // или clone_slide + ref на слайд-пример
  "slots": [
    {"role": "title", "bbox": [0.062, 0.083, 0.876, 0.12], "style": "title",
     "size_pt": 32, "font": "Bahnschrift",     // фактические, а не эталонные для роли
     "ph": {"type": "title", "idx": 0}, "capacity": {"chars": 62, "lines": 2}},
    {"role": "metric_value", "group": "kpi", "index": 0,
     "bbox": [0.062, 0.31, 0.27, 0.18], "style": "metric_value",
     "capacity": {"chars": 6, "lines": 1}},
    {"role": "metric_label", "group": "kpi", "index": 0,
     "bbox": [0.062, 0.49, 0.27, 0.10], "style": "body_l1",
     "capacity": {"chars": 48, "lines": 2}}
  ],
  "repeat": {"group": "kpi", "min": 2, "max": 4,
             "step": {"dx": 0.307, "dy": 0.0}},   // как размножается колонка
  "accepts": {"blocks": ["metric"], "min": 2, "max": 4, "needs_image": false},
  "fit": {"autofit": "shrink", "min_size_pt": 14, "shrink_step": 0.9},
  "preview": "previews/metrics-3.png"
}
```

`capacity.chars` не выдумывается: считается по реальным метрикам шрифта
(fontTools) для ширины блока при заданном кегле, а затем сверяется с длиной
текста в самом шаблоне — если дизайнер положил туда 80 символов, значит влезает.

**Определение архетипа** — гибрид: сначала признаки из XML (тип и число
плейсхолдеров, доля площади под картинку, число повторяющихся групп, наличие
таблицы/графика), затем, если уверенность низкая, VLM смотрит на рендер слайда и
выбирает архетип из словаря. Модель **не** решает, как слайд выглядит, — только
как он называется по смыслу.

**Повторяющиеся группы** (три колонки, четыре карточки) распознаются
кластеризацией шейпов по одинаковым размерам и равному шагу — это даёт паттерну
эластичность: тот же паттерн умеет и 2, и 4 элемента.

## 5. Content IR (выход шага 4)

Единое представление входного контента, независимое от формата файла.

```jsonc
{
  "meta": {"language": "ru", "title": "Платформа X", "words": 1840},
  "assets": [{"id": "img1", "path": "…", "w": 1600, "h": 900, "kind": "photo"}],
  "blocks": [
    {"id": "b1", "type": "heading", "level": 1, "text": "Платформа X"},
    {"id": "b2", "type": "paragraph", "text": "…", "importance": 0.8},
    {"id": "b3", "type": "list", "items": ["…", "…", "…"], "ordered": false},
    {"id": "b4", "type": "metric", "value": "3.2×", "label": "быстрее сборки"},
    {"id": "b5", "type": "table", "header": ["…"], "rows": [["…"]]},
    {"id": "b6", "type": "series", "x": ["Q1", "Q2"], "y": {"Выручка": [12, 19]},
     "suggest": "bar"},
    {"id": "b7", "type": "quote", "text": "…", "author": "…"},
    {"id": "b8", "type": "steps", "items": ["…", "…"]}
  ]
}
```

Разбор детерминированный: Markdown/docx → заголовки, списки, таблицы;
xlsx/csv → `series`/`table`; регулярки вытаскивают метрики вида «`3.2×`»,
«`+18 %`», «`450 млн ₽`» из текста. LLM только дополняет: важность блока,
язык, скрытая структура в «рыхлом» тексте.

## 6. План презентации (выход шага 5) и подбор (шаг 6)

LLM получает Content IR (без разметки шаблона!) и бриф, возвращает по строгой
схеме:

```jsonc
{"slides": [
  {"n": 1, "intent": "cover", "key_message": "Платформа X сокращает сборку в 3 раза",
   "blocks": ["b1"], "notes": "…"},
  {"n": 4, "intent": "metrics", "key_message": "Эффект в цифрах",
   "blocks": ["b4", "b4a", "b4b"]}
]}
```

Модель **не знает**, какие макеты есть в шаблоне — иначе она начнёт «дизайнить».
Сопоставление плана с библиотекой паттернов — детерминированный скоринг:

```
score(pattern, slide) = 2.0·archetype_affinity(pattern.archetype, slide.intent)
                      + 1.5·capacity_fit(pattern, blocks)      // влезает без сокращений
                      + 0.7·asset_fit(pattern, blocks)         // есть картинка ↔ есть слот
                      − 1.0·repeat_penalty(pattern, prev_slides)
                      − 2.0·overflow_risk(pattern, blocks)
```

Венгерский алгоритм по всей колоде, а не жадный выбор по слайду: это убирает
ситуацию «первые слайды забрали лучшие паттерны». Каждое назначение пишется в
трейс с разложением скоринга — это и есть объяснение «почему такой макет».

## 7. Сборка (шаг 8)

**База.** Выходной файл — это **копия шаблона**, из которой удалены
слайды-примеры. Так наследуются тема, мастера, макеты, встроенные шрифты,
размер слайда и настройки — ничего не нужно воспроизводить руками.

**Два режима на слайд.**

| Режим | Когда | Как |
|---|---|---|
| `use_layout` | Паттерн снят с макета и макет полный | `add_slide(layout)` и заполнение плейсхолдеров; всё форматирование наследуется |
| `clone_slide` | Паттерн снят со слайда-примера (дизайн нарисован руками) | Глубокая копия части `slideN.xml` с медиа и связями в новый пакет, затем подмена текста в ранах с сохранением `rPr`, подмена картинок через `r:embed` |

`clone_slide` — то, что даёт визуальную точность на «живых» шаблонах, где макеты
пустые, а вся красота на слайдах. Реализуем через `sd/ooxml/clone.py`: копия
элемента `<p:sld>`, перенос rels, дедупликация медиа по хешу.

Графики вставляем нативными (`chart part`), без картинок: они автоматически
берут акценты темы, и в PowerPoint их можно править. Таблицы — с явной заливкой
из ролей палитры.

## 8. Рендер и CV (шаги 2, 9)

| Бэкенд | Точность | Когда |
|---|---|---|
| PowerPoint COM (`Presentation.Export`) | эталон | Windows + установлен Office — наш случай для разработки |
| LibreOffice headless (`--convert-to pdf` + PyMuPDF) | высокая | переносимый вариант, для машины жюри и CI |
| Встроенный SVG-рендер по разложенным боксам | приблизительная | нет ни того, ни другого: геометрия и переполнения считаются, декор — условно |

CV поверх рендера: карта яркости фона под каждым текстовым блоком (выбор
светлого/тёмного начертания и проверка контраста), детект переполнения
(непустые пиксели за границей бокса с допуском на свисающие элементы букв),
детект коллизий, ΔE-сравнение палитры факта и шаблона.

## 9. Нормоконтроль и ремонт (шаги 9–10)

Проверки из `01-task-analysis.md` §5 запускаются послайдово. При дефекте —
лестница исправлений, каждая ступень дешевле следующей:

1. уменьшить кегль в пределах `fit.min_size_pt`;
2. срезать до `capacity` по словам (без LLM) — только для хвостовых элементов
   списка;
3. попросить LLM переписать текст короче с сохранением смысла (лимит символов —
   в промпте, проверка — после);
4. сменить паттерн на следующий по скорингу с большей ёмкостью;
5. разбить слайд на два.

Всё, что не удалось починить, попадает в отчёт с координатами и скриншотом —
чтобы «без ручного редактирования» было проверяемым утверждением, а не лозунгом.

## 10. LLM-слой

Один интерфейс `LLMProvider.complete(messages, schema) -> dict`. Реализации:
`openai_compatible` (`base_url`, `model`, `api_key` из `.env` — под API
организаторов), `anthropic`, `stub` (детерминированные ответы для тестов и
офлайн-демо). Все вызовы: строгая JSON-схема, до 2 повторов при невалидном
ответе, кеш по SHA-256 (промпт + схема + модель) в `.cache/llm/`. Промпты лежат
в `sd/llm/prompts/*.md` — версионируются как код.

## 11. CLI и API

```bash
sd analyze <template.pptx> [--out design_system.json] [--previews]
sd build <template.pptx> <content.md> [--brief brief.yaml] [--out deck.pptx]
sd evaluate <deck.pptx> --template <template.pptx>       # метрики §5
sd matrix <content.md> --templates templates/            # тот же контент × все шаблоны
```

API повторяет CLI: `POST /templates` (анализ и превью), `POST /decks`
(генерация, стрим прогресса по SSE), `GET /decks/{id}` (метрики и файл).

## 12. Тесты

- **Инварианты, а не золотые файлы:** для любого шаблона из набора — палитра
  непуста, у каждого паттерна ≥ 1 слот, `safe_area` внутри слайда.
- **Свойство «не зашито»:** AST-линтер по `sd/compose`, `sd/plan`, `sd/fit` —
  никаких HEX, имён шрифтов и абсолютных EMU-координат.
- **Кросс-шаблонный тест:** один контент × все шаблоны → у всех колод ноль
  дефектов и разные дизайн-системы (проверяем, что JSON-ы действительно разные).
- **Регресс на укладку:** синтетические тексты растущей длины — проверяем, что
  ремонтная лестница всегда сходится.
